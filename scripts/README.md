# `scripts/`

Repo-wide tooling — scripts that operate across the whole OtoDock stack rather
than inside any single service (`proxy/`, `dashboard/`, `phone/`, `satellite/`,
`audio/`). They live at the repo root alongside the other whole-stack artifacts
(`docker-compose*.yml`, `VERSIONS.md`, `config.env.example`).

## Install / host setup

| Script | Purpose | Consumed by |
|--------|---------|-------------|
| `install.sh` | One-command bootstrap for the Docker quick start: preflights Docker/Compose (Engine 26 and Compose 2.26 or later since 1.9.0, before anything is written), installs into the directory it is run from (refuses `$HOME`; `OTODOCK_DIR` honored as a legacy override), writes `.env` with a generated Postgres password, handles the Ubuntu 24.04+ userns step (fetches + runs `setup-apparmor-userns.sh` under one sudo prompt), fetches the release-pinned `docker-compose.yml` + the phone overlay (enabled via `COMPOSE_FILE` in the generated `.env`; remove it from that line to opt out), writes `COLLABORA_SSL_TERMINATION` from `.env`'s `DASHBOARD_PUBLIC_URL` and starts the stack. The `COMPOSE_FILE` line it writes is base first, with a `docker-compose.override.yml` already in the folder listed last. Fresh installs only: it refuses to touch an existing one (`upgrade.sh` moves one to a newer release); idempotent on re-run after a stop. | self-host operators (fetched raw from GitHub, per the README quick start) |
| `upgrade.sh` | Moves a Docker quick-start install to a newer release (`--to <version>`, default the latest; `--dry-run` prints every step and changes nothing). Run from the install folder. In order: downloads the release's `docker-compose.yml` + `docker-compose.phone.yml` and checks the files the upgraded stack loads against the install's own `.env` (`docker compose --env-file ./.env ... config -q`) before any change, so a value the new files refuse (a hostname in `OTO_AUDIOSOCKET_PUBLIC_HOST`) stops it with nothing touched; with the phone overlay in use, an unset `OTO_PHONE_BIND` and an IPv4 `OTO_AUDIOSOCKET_PUBLIC_HOST` this host does not hold (`ip -o -4 addr`) draw a warning (the phone container would not start); for a target of 1.8.0 or later names the `.env` yes/no values that count as on from 1.8.0 and stops on a value the target refuses (the dry run warns); prints the Upgrade notes of every release the upgrade crosses, from the target's `CHANGELOG.md`; dumps the database to `backups/upgrade-<time>/` (`--no-db-backup` skips it) and copies `.env` and the compose files there, plus, beside a dump, a `manifest` that makes the folder a `restore.sh` run directory; replaces the compose files; sets `OTODOCK_VERSION=<target>` in `.env`, `COMPOSE_FILE` when a file must be listed (base first, then the phone overlay when in use, then an existing override, no file twice) and `COLLABORA_SSL_TERMINATION` when it disagrees with the scheme of `DASHBOARD_PUBLIC_URL` (1.9.0). It writes no other line of `.env`: the names of settings new in the release are printed, never appended. Then `docker compose pull` and, since 2.0, the wait for open work: a running server of 2.0.0 or later is asked to wait for its chats and tasks and to hold what is new (`admin_cli.py drain` in its container, up to `OTODOCK_DRAIN_BOUND_S` seconds, the shell's value, else `.env`'s, else 600), its lines printed as the script's own. A silent server is asked again for about a minute. A server that does not answer, is not running or is older than 2.0 draws a warning in its own sentence and the upgrade goes on, and the drain is called off (`resume`) when the run stops before the swap or the swap is rolled back. The old server's last 1,000 log lines are kept as `otodock-proxy.log` in the run's folder, from any release. A server older than 2.0.0 is asked nothing: before the dump, and in the dry run, the script says that the chats and tasks running at the update are cut and do not continue by themselves, and at a terminal it leaves ten seconds to stop. Then a stop of Collabora, `docker compose up -d --remove-orphans`, and a wait for the proxy's healthcheck. A failure before `up` puts the files back (nothing migrated), and so does an `up` that fails before anything of the new release ran: the script then also removes the containers that start created and never ran, gives the old ones it renamed `<12 hex>_<name>` their names back, starts the old release again and says what failed. A failure once anything of the new release has started leaves the new files in place, since the database may be migrated, and names the folder to restore with `restore.sh`. Before the dump and the pull it also compares what an override mounts for `otodock-proxy` with `otodock-compute` (`compose_mounts.py`, run with the server container's own image, no network). A folder or an engine mounted for the proxy alone stops the update, with the mounts and the command of the next run named. The dry run warns. With no server container the pulled image runs the compare after the pull. A sandbox privilege an override still gives the proxy is named once. `OTODOCK_COMPOSE_PROJECT` names the compose project (default: the one compose resolves for the folder, `otodock`), as for `backup.sh`. When compose refuses the folder's files, the project is the one the folder's own containers carry. With none or two of them the script stops: it never starts a stack under a guessed name. Refuses a source checkout and a downgrade (a target below `.env`'s version or below the release the database records). `--compose-dir <folder>` (with `--to`) reads the compose files, `config.env.example`, `CHANGELOG.md` and `scripts/compose_mounts.py` from a folder instead of the release, for testing a release candidate, and runs images present only locally. A release candidate target (`X.Y.Z-rcN`) prints the upgrade notes and release links of the release it precedes. | self-host operators (fetched raw from GitHub, like `install.sh`) |
| `install-baseline-tools.sh` | Installs the baseline dev toolchain (git, gh, python+uv, node+pnpm, ripgrep, …) every agent sandbox expects. Below `PASST_MIN_VERSION` it builds the pinned passt from its tag (`OTODOCK_PASST_BUILD`: `auto`, `required`, `distro`; VERSIONS.md). | `satellite/install.sh`, the platform `proxy/Dockerfile` |
| `install-baseline-tools.ps1` | Windows (winget) equivalent of the above, for Windows satellite hosts. | `satellite/install.ps1` |
| `oto-git-credential-helper` | The host's git credential helper for `github.com`, installed into `/usr/local/bin` and wired into `/etc/gitconfig`; it reads a `GH_TOKEN` from the environment. A platform session resets it and names its own credential helper (`proxy/hooks/credential_helper.py`), so it serves a shell outside the platform's sessions only. | installed by `install-baseline-tools.sh` |
| `setup-apparmor-userns.sh` | One-time host setup for Ubuntu 24.04+ (`kernel.apparmor_restrict_unprivileged_userns=1`): installs + loads the scoped `otodock_userns` AppArmor profile so the compute container can create the unprivileged user namespaces the agent sandbox is built on — WITHOUT disabling the system-wide hardening. Self-contained (the pull-only compose flow fetches just this file); idempotent; no-ops on hosts without the restriction. | self-host operators (`sudo`); run automatically by `compose.sh` when needed |
| `setup-host-tuning.sh` | One-time host tuning that keeps the platform out of swap: writes `/etc/sysctl.d/90-otodock.conf` with `vm.swappiness=10` and applies it at once, so a memory burst from a sandboxed tool container cannot park the server's worker processes in swap and stall the dashboard on the page-in. Self-contained (the pull-only compose flow fetches just this file); idempotent; non-Linux hosts and a host already at 10 or below are left untouched; a higher-sorted drop-in in `/etc/sysctl.d/` overrides it. | self-host operators (`sudo`) |
| `sandbox-doctor.sh` | Read-only sandbox diagnosis (no root, writes nothing): host facts (userns sysctls, AppArmor profiles, tool versions) + the namespace probe ladder — `unshare -Urn`, one-level bwrap with the session flags, nested bwrap, Codex's npm-vendored bwrap — ending in a copy-paste report block. Run it on the host (T1) or with `docker compose exec otodock-compute` (T2/T3) when sessions do not start. | self-host operators |

## Compose / version pinning (self-host)

| Script | Purpose | Consumed by |
|--------|---------|-------------|
| `versions.sh` | Parses the pinned image/CLI versions out of [`VERSIONS.md`](../VERSIONS.md) (the single source of truth) and exports them. Sourceable, or `versions.sh KEY` to print one. | `compose.sh`; mirrors `proxy/config.py::_read_pinned_version` |
| `compose.sh` | `docker compose` wrapper for the fully-containerised stack: checks for the `docker` CLI + compose v2 plugin up front (clear error instead of a raw `exec` failure), stacks `docker-compose.yml` + `docker-compose.build.yml` (+ `docker-compose.phone.yml` when present) and sources `versions.sh` so the image build stays in lockstep with `VERSIONS.md`. On Ubuntu 24.04+ it also selects the `otodock_userns` AppArmor profile (via `OTODOCK_APPARMOR_PROFILE`), running `setup-apparmor-userns.sh` (sudo) itself when the profile isn't installed yet. Since 1.9.0 it exports `COLLABORA_SSL_TERMINATION` from the scheme of `config.env`'s `DASHBOARD_PUBLIC_URL` (a value set in the shell wins) and, for `up`, `create`, `run` and `start`, refuses a Docker Engine older than 26 or a Docker Compose older than 2.26. | self-host operators |
| `copy-tools-to-compute.sh` | Copies the community tools the server's volume holds into the compute service's own tools volume, once: every Python or Node tool's folder and the community interpreters. It never copies a Docker tool, a backup, a failed install, a staged folder or another hidden entry. Writes its mark last. A tool the compute volume already holds is left as it is. Exit 3 with one line when the volume is too small, 1 when a folder could not be copied. | the `otodock-tools-copy` one-shot of `docker-compose.yml` (uid 1000, the two tools volumes alone), at every start |
| `remote-compute-install.sh` | Adds a server as a compute machine of an install. It checks the server, makes the machine's secret there and sends only its hash to pair. Then it starts the platform's image under the systemd unit `otodock-remote-compute.service`. | served by the platform's `/v1/satellite/bootstrap` with `otodock-remote-compute.sh` and `setup-apparmor-userns.sh`, run with sudo from the command the Compute card shows |
| `otodock-remote-compute.sh` | The host service of a compute machine on another server, installed as `/opt/otodock-remote-compute/otodock-remote-compute`. `run` starts the platform's image in a container. When the machine exits, it asks the platform which image tag to run and whether an admin removed the machine. `remove` takes away everything the machine keeps on the server. `status` says what runs. | the unit `otodock-remote-compute.service`, and admins by hand for `remove` and `status` |
| `compose_mounts.py` | Reads `docker compose config --format json` on its input. Prints a line for each shared folder or engine that `otodock-proxy` mounts and `otodock-compute` does not mount the same. Then `proxy: <item>` for each privilege of the sandbox the proxy still holds. An admin's own hardening is never named. Nothing printed when both services agree. Standard library only, since another release's Python runs it. | `upgrade.sh` |

## Development bootstrap

| Script | Purpose | Consumed by |
|--------|---------|-------------|
| `generate-openapi.py` | Writes `proxy/api/public/openapi.json`, the description of the public API, from the listed routes alone. Run it with the proxy's venv after changing a public route; a test fails while the committed file differs. | developers / contributors |
| `dev-setup.sh` | One-shot DEV bootstrap for the bare-metal (host-process) install (`--service` = generate+enable systemd unit(s) for this checkout; `--phone` = include the telephony daemon): pinned Node/Python/uv/pnpm from `VERSIONS.md`, baseline tools + Docker, proxy venv + `proxy/setup.sh` (config.env), Postgres via `docker-compose.t1.yml`, dashboard build. Idempotent — re-run it after `git pull` to reconcile the toolchain, with the proxy and the compute unit stopped: a re-run rebuilds a venv whose Python is not the pin (a patch release included) and recreates the Postgres container on a new `POSTGRES_IMAGE` (its data kept), and it stops while the `otodock-proxy` or `otodock-compute` unit (with `--phone`, also `otodock-phone`) is active, moves Node to the pinned major through one NodeSource source, and stops before any change on a `node` outside `/usr` (a version manager's). NOT the production installer (no sudoers/quota tooling; production = Docker Compose). | developers / contributors |
| `prose/prose_check.py` | Checks every page written for people against the writing rules of [`WRITING.md`](../WRITING.md). The words and caps are in `prose/rules.json`, and `.prose.json` names the pages. `--file` checks a few pages, `--self-test` the rules themselves. | contributors, CI's `prose` job, the release gate |

## Database backup / restore

| Script | Purpose | Consumed by |
|--------|---------|-------------|
| `backup.sh` | One run directory per backup, `backups/otodock-<version>-<time>/`: the database (`db.sql.gz`, `pg_dump --clean --if-exists` through `docker exec`), the env file (`env`, 0600: every secret), the agents tree (`agents.tar.gz`: every SQLite database copied through the backup API, links kept), the ssh keys (`ssh-keys.tar.gz`) and the sessions tree (`sessions.tar.gz`: the connected OAuth accounts' token files, the only copy of them), with a `manifest` naming the release, the topology and the credential key fingerprints. `--db-only` writes the dump, the env file and the manifest. Honours `OTODOCK_BACKUP_DIR`, `OTODOCK_BACKUP_RETAIN` (14 runs), `OTODOCK_BACKUP_RETAIN_TREES` (the trees of the 3 newest), `OTODOCK_COMPOSE_PROJECT` (the compose project; set, no container is found by its bare name), `OTODOCK_POSTGRES_CONTAINER` (a Postgres that is not the project's `otodock-postgres` service), `OTODOCK_ENV_FILE`, `OTODOCK_AGENTS_DIR`, `OTODOCK_SSH_KEYS_DIR` and `OTODOCK_SESSIONS_DIR` (bare metal). Retention runs first and touches only directories named like a run, removing the files the script writes. On the containerised stack the trees are read inside the running proxy container or through a one-off container on its image when it is stopped. Exit 0 whole, 3 when a file or database could not be copied (named on stderr, the archive holds the rest) or when the tree did not fit the output disk (the dump, the env file and the manifest are written), 1 on any other failure with the run directory removed. The flat files of earlier releases are left alone. | operators (cron / systemd-timer) |
| `restore.sh` | Restores a `backup.sh` run directory (the database, the agents tree, the ssh keys and the sessions tree; a run without `sessions.tar.gz` restores the rest and says the connected OAuth accounts need connecting again) or a bare dump (the database alone), destructive, with a confirmation. Refuses while the platform runs (the project's proxy container running, restarting or paused on Docker; on bare metal the port the env files publish), a backup from a newer release than the running images (`--allow-newer` warns instead), a backup whose credentials were encrypted under keys this install lacks, naming them (`--ignore-credential-key` restores anyway, every stored credential unreadable), and an archive that fails its check (a member under an archived link, `..`, a FIFO, a hard link outside the root, or more bytes than the volume has free). Recreates the `public` schema before feeding the dump (a failed recreation stops it); reads every archive in full before moving the current tree aside and extracting it (through a one-off container on the proxy image on Docker). `--db-only` leaves the trees alone. An `upgrade.sh` snapshot (`trees=none`, or a 1.8.x one by its manifest or its `upgrade-<TS>` folder) brings back the database only; the script says so, says that going back to its release means copying `.env` and the compose files from the snapshot first, and that the running release migrates an older snapshot's database forward again at its next start. A 1.7.1 `otodock-apps-<TS>.tar.gz` is restored by hand after its dump, with the proxy still stopped: `tar -xzf otodock-apps-<TS>.tar.gz -C <agents dir>` as the proxy's user on bare metal, or `docker run --rm -i --user 0 -v otodock-agents:/agents --entrypoint sh ghcr.io/otodock/otodock-proxy:<version> -c 'tar -xzf - -C /agents && chown -R 1000:1000 /agents' < otodock-apps-<TS>.tar.gz` on the containerised stack. After a restore no cut turn continues by itself: `restore.sh` deletes the three `platform_settings` keys that say when the platform was last alive, so at the next start a chat asks for a message, a task's run fails with its report, and no one-time task fires for the time that passed. The backup's stored wakes and queued messages still go out and start turns. A database restored by hand, or a disk snapshot brought back, keeps the marks of its moment: delete `platform_alive_at`, `platform_held_at` and `platform_clean_stop` from `platform_settings` before its first start, or a copy less than a day old continues its open turns as after a crash. | operators |
| `otodock-admin.sh` | The admin command line, for the day nobody can sign in: `user reset-password <email>` (a temporary password printed once, or `--password-stdin` to set one, asked without echo at a terminal), `user disable-2fa <email> [--passkeys]`, `support-info` (versions, counts and the settings, every secret left out: for a bug report), `jobs list` and `jobs run <job>` (the minute jobs that need no server state). Since 2.0 also `status` (one line: idle, or what is working), `drain [--bound SECONDS] [--away SECONDS] [--quiet] [--probe]` (holds new work at once, waits for the open work up to the bound, `OTODOCK_DRAIN_BOUND_S` or 600 seconds, and goes on holding until the platform restarts, 15 minutes at most with no stop; exit 0 once it holds, 1 when the server stays silent for about a minute or refuses the key, 3 when no server runs, 4 from a source checkout older than 2.0, 2 on a Docker install older than 2.0, whose command line has no such command) and `resume` (calls a drain off) and `compute [--wait SECONDS]` (whether the compute machine is signed in: exit 0 signed in, 1 not). The four ask the running server with the master key on its own address and read no database. On a Docker install it runs `proxy/admin_cli.py` inside the install's own running `otodock-proxy` container (the compose project's, started from this folder; `OTODOCK_COMPOSE_PROJECT`), so no database password is typed; in a source checkout it runs it with `proxy/venv` (`OTODOCK_ADMIN_MODE=docker|source` forces one). Each change writes one line to the platform's log naming the command line's user and host (the password reset in the dashboard's own words, 2FA and passkeys with the command line as the actor). Before a change it prints the config file and the database it is about to change (host, port and name, never the password). Exit 0 done, 1 refused, 2 usage, and for `status`, `drain` and `resume` 3 no server runs, 4 older than 2.0. Since 1.9.0. | operators (fetched raw from GitHub for the release the install runs) |

## Maintainer tooling

| Script | Purpose | Consumed by |
|--------|---------|-------------|
| `sync-satellite-code.sh` | Vendors the shared proxy modules into `satellite/_vendored/` (byte-identical copies) and updates the `SHARED_*_HASH` constants in `satellite/config.py` so the satellite detects drift at import. **Run this after editing any shared module — never edit the vendored copies directly.** | maintainers |
| `loadtest_sessions.py` | Concurrency load-test + memory/CPU calibration harness for the live-RAM admission gates (`SESSION_EST_*_MB` in `proxy/config.py`). Spawns K concurrent sessions through the real dashboard WebSocket and measures the proxy process tree. | maintainers (sizing/calibration) |
| `image-boot-check.sh` | Boots the three release images (`image-boot-check.sh PROXY_IMAGE FILE_TOOLS_IMAGE PHONE_IMAGE`) on a throwaway network with a Postgres at `VERSIONS.md`'s `POSTGRES_IMAGE` and proves each one answers its `/health`: the proxy as the compose file runs it, with no security option and no device, whose container must not start the sandbox's shape. The same image then starts as the compute service, with the security options and the tun device. A host without `/dev/net/tun` stops the check first, naming the device. There pasta must be `PASST_VERSION` and must run the sandbox's shape, the netns launcher wrapping bwrap, and the compute service's own start check must answer ok. Then the phone service once the proxy has pushed its configuration, the file tools with the headless browser present. Each image's version label must equal `OTODOCK_VERSION`. No host port, random names, the containers and the network removed on exit, the log tails printed on a failure; `OTODOCK_BOOT_WAIT_S` (900) and `OTODOCK_BOOT_SERVICE_WAIT_S` (180) set the budgets. | `.github/workflows/release-images.yml` (each architecture, before a version tag points at the images); maintainers on a local build |
| `build-wasm-kws.sh` | Rebuilds the wake-word WASM keyword-spotting bundle in `proxy/assets/kws/` (sherpa-onnx, emsdk and the GigaSpeech keyword model pinned in its header; `bpe.model` and `tokens.txt` also copied for the proxy's keyword encoding), after applying `kws-no-encoder-reset.patch` to the sherpa-onnx checkout (the spotter's automatic reset keeps the encoder states); stops when the patch does not apply. A rebuild lands in a new versioned directory, and the dashboard's asset path follows it. | maintainers (a sherpa-onnx, model or patch change) |
